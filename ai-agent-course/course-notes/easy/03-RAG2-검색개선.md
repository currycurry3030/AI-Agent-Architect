# 3교시 · RAG 2 — 쉬운 설명 버전

## 이번 시간의 핵심은 "기법"이 아니라 "순서"

문제 있는 결과물을 받았을 때 디자이너도 이렇게 하시죠 — **뭐가 이상한지 보고 → 원인을 찾고 → 고치고 → 진짜 나아졌는지 다시 확인.** 오늘 배우는 것도 똑같은 순서입니다. 아래 3가지 기법은 도구일 뿐이고, **이 순서 자체가 진짜 배울 것**입니다.

```
증상 확인 → 원인 찾기 → 처방 → 정말 나아졌는지 재확인
```

## 증상 ① — 근거는 2개인데 답은 1개만 나온다

예를 들어 같은 항목인데 문서 버전(A안/B안처럼)이 두 개 있으면, AI가 둘 중 하나만 골라 답하거나 섞어버릴 수 있습니다.

**원인을 가르는 법**: AI가 참고한 근거 조각을 직접 열어봅니다. 답변 내용이 근거 안에 실제로 있으면 "AI가 요약을 잘못한 것"이 아니라 **"애초에 검색이 애매한 조각을 가져온 것"**입니다.

## 처방 1 — Reranking (2차 심사)

1차 검색은 "얼추 비슷한" 후보를 빠르게 여러 개 골라옵니다. Reranking은 그 후보들을 **질문과 하나씩 다시 대조해서 진짜 딱 맞는 것만 위로 올리는 2차 심사**입니다.

Midjourney에서 4장 뽑고 그중 하나를 Upscale하는 것과 비슷합니다 — 1차는 넉넉하게 뽑고, 2차는 그중 진짜 쓸 것만 고르는 것.

> 2차 심사는 비용이 더 듭니다(느림). 그래서 1차에서 후보를 넉넉히 뽑아둬야 2차가 진짜 정답을 놓치지 않습니다.

## 처방 2 — Metadata Filter (태그로 미리 거르기)

라이트룸에서 별점이나 태그로 사진을 미리 걸러놓고 찾는 것처럼, 문서마다 붙어있는 "출처·페이지·버전" 같은 꼬리표로 **찾을 범위 자체를 좁히는 것**입니다. "이 문서 안에서만 찾아줘"라고 미리 정해두는 것과 같습니다.

## 어떤 처방을 써야 할까 — "증상에 맞는 처방"

- 근거가 섞여서 순위가 헷갈리는 문제 → **Reranking**
- 애초에 참고하면 안 되는 문서(다른 버전 등)가 섞이는 문제 → **Metadata Filter**

**맞지 않는 처방을 쓰면 느려지기만 하고 문제는 그대로**입니다. 진단을 먼저 하고 처방을 고르는 순서가 중요합니다.

## 증상 ② — 짧은 검색어가 헛돈다

`6.2.1.1`처럼 숫자만 있거나, `박리`처럼 한 단어짜리 검색어는 "뜻 좌표(임베딩)"가 거의 안 잡힙니다. 사람은 맥락을 알고 검색했지만, 그 맥락이 검색어 자체엔 없기 때문입니다.

## 처방 3 — Query Rewrite (검색어를 AI가 다시 써줌)

검색하기 전에, AI에게 "이 저장소엔 이런 문서들이 있다"고 미리 알려주고 검색어를 더 명확하게 다시 쓰게 합니다. 애매한 요청("느낌 있게")을 구체적인 요청("따뜻한 톤, 필름 그레인, 낮은 채도")으로 바꿔주는 것과 비슷합니다.

## 나아졌는지는 어떻게 아나 — 채점표 만들기

느낌으로 "좋아진 것 같다"는 근거가 안 됩니다. 정답을 아는 질문 세트를 미리 만들어두고, **AI에게 채점까지 시켜서(LLM-as-a-Judge)** 점수를 숫자로 남깁니다.

- 처방 걸기 전 점수를 먼저 재둡니다 (기준선)
- 처방을 하나씩만 켜서 비교합니다 (한 번에 여러 개 바꾸면 뭐 때문에 좋아졌는지 알 수 없음)
- 채점한 AI도 가끔 틀리니, 이상한 점수는 사람이 직접 확인합니다

## 정리

- 기법을 아는 것과 **어떤 증상에 어떤 기법을 쓰는지 아는 것**은 다릅니다
- 맞지 않는 처방은 느려지기만 합니다
- **재보지 않으면 고친 건지 망친 건지 알 수 없습니다**
