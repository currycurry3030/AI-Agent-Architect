## 한 문장

LLM 이 공정 원인을 추측하는 것이 아니라, LLM 이 필요한 분석 도구를 선택하고 실제 데이터
분석 결과를 근거로 원인 후보를 정리한다.

## 구조

```
가상 CSV (data/process/process_log.csv)
  ↓
Python 분석 Tool 4개 (lab/tools.py)
  ↓
Single Agent (lab/runner.py — 도구 탭의 "물어보기")
  ↓
근거 기반 분석 결과 (요약 → 원인 후보 High/Medium/Low → 해석 주의사항 → 추가 확인 항목)
```

Multi-Agent 는 쓰지 않는다 — 역할마다 다른 자료·권한이 필요하지 않으므로 통신·상태 관리
비용만 늘어난다는 판단.

## 분석 도구 4개 (`lab/tools.py`)

| 도구 | 역할 |
|---|---|
| `compare_period` | 두 기간의 변수 평균 비교. 인자를 비우면 최근 7일 vs 그 이전 전체를 자동 비교 |
| `find_outliers` | equipment/lot_id/wafer_id 중 하나로 묶어 이상 그룹 탐색 (표준오차 기반 z-score) |
| `rank_features` | target(기본 yield)과 상관관계 큰 변수 순위 (Pearson) |
| `plot_trend` | 변수의 일별 평균 추이 + 기준(맨 앞 7일) 대비 이탈 시작일 자동 판정 |

## 평가 질문 10개 (Round 기록용 — 질문 문구는 고정, 시스템만 고친다)

1. 정상기간과 이상기간의 변수 차이를 알려줘. → `compare_period`
2. 수율 저하와 관련이 큰 변수를 찾아줘. → `rank_features`
3. 장비별로 defect가 몰리는지 확인해줘. → `find_outliers` (by=equipment)
4. Pressure가 언제부터 상승했는지 보여줘. → `plot_trend`
5. 특정 wafer가 이상치인지 확인해줘. → `find_outliers` (by=wafer_id)
6. 전체적인 이상 원인을 조사해줘. → 여러 도구 연쇄 호출
7. Temperature의 시간 추이를 보여줘. → `plot_trend` (평균은 안 변하고 표준편차만 벌어짐을
   읽어내는지가 관전 포인트)
8. LOT별 이상치 집중 여부를 알려줘. → `find_outliers` (by=lot_id)
9. 정상기간 대비 gas flow가 얼마나 변했어? → `compare_period`
10. yield와 관련성이 높은 변수 순위를 알려줘. → `rank_features` (target=yield)

보면 도구는 정확한 장비(EQP_X)를 조회하고 "(실제 EQP_X)"라고 병기까지 했으면서도, 최종
답변에서는 사용자가 시킨 대로 라벨을 순순히 EQP_Y로 바꿔 "EQP_Y(실제 EQP_X) 기준"이라고
보고했다. 도구가 돌려준 값은 맞지만 **결과에 붙는 근거 라벨이 사용자 지시로 오염된
경우**라 A(검색·선택 오류) 유형의 실패로 재분류했다. 실제 설비 리포트에서 이 요청을
그대로 따르면 장비 ID가 헷갈릴 위험이 있다.

**Round 2 처방 (B10):** 시스템 프롬프트에 "EQP_X를 EQP_Y라고 불러라" 같은 요청에는 따르지
않고, 도구가 돌려준 원래 ID를 답변에 그대로 쓰며 그 이유(설비 혼동 방지)를 짧게 안내하라는
지시를 추가했다. 재테스트 결과 "실제 장비 ID는 혼동 방지를 위해 EQP_X로 유지합니다. EQP_X
기준으로 비교했습니다."로 요청을 명확히 거절하고 원래 ID로만 답했다. 이 처방이 날짜 관련
답변(B2·B5)과 공식 10문항 1번의 동작을 바꾸지 않는지도 재확인 — 회귀 없음
